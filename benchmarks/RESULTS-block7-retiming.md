# Block 7 — what the two retiming readings cost in overlapping cards

Generated by `npm run retiming`. Free, local, read-only: no plan is modified and
no API is called. Every figure here is emitted by the tool.

## The question

TEMPLATE_LIBRARY_GUIDE §5 says the system places an instance so its **intro ends**
when the element should be fully on. With `outroS: 0` — which all six built comps
declare — the structure is intro + hold and the card hard-cuts out, so that reading
gives `inPoint = displayStart − introS`.

Every subtitle card sits at the same place on screen (PROJECT_SPEC §5 fixes the
subtitle position globally). So a card whose intro begins while the previous card
is still held is **two cards stacked on one another** at the same position.

The alternative reading, `inPoint = displayStart`, spends the intro inside the
display window: nothing ever overlaps, but the words are not fully legible until
`introS` after they are spoken.

**This file counts. It does not recommend.** Which reading is right is a judgement
on a built comp.

## What was measured

- Every `.editplan.json` in `my files/test videos/` carrying subtitle groups: **5 reels**.
- **Consecutive pairs only.** Subtitle groups come from one word sequence and never
  reorder, so a card can only collide with its neighbour.
- Intro per group from its own `templateId` in `templates/manifest.json`. 42 groups carried
  no template and used the subtitle fallback of 0.13 s (every subtitle template declares the same value, so the fallback is not a guess).
- The display window is `displayStart`/`displayEnd` where present and the speech
  window otherwise, which is what `displayWindow` does at build time.

**No plan in the corpus stores display timing** — `displayStart` is absent on every
group of every reel, so every figure below is measured on speech windows. When
display timing is written, extension into silence pushes `displayEnd` later and
these overlap counts can only rise.
